**QA verdict: not ready for production or real payment processing.**

Assessment date: September 25, 2026. Reviewed the Express API, PostgreSQL schema and fallback store, React administrative portal, and Expo tenant application. Existing user changes were preserved; application code was not fixed or changed during this assessment.

The main release blockers are unauthorized administrator creation, password bypasses, tenant data exposure, and payment settlement without verified funds. Presentation is generally consistent on desktop, but reliability and financial correctness currently undermine user trust.

These were deliberately selected defect probes, not a representative pass-rate score. The scripts record expected-behavior failures in JSON and can finish with exit code 0 despite findings. Build success does not establish workflow correctness.

Browser coverage included login, dashboard, stalls, tenants, applications, payments, maintenance, announcements, reports, users, and new-stall/new-tenant forms. Layouts were inspected at 1440 and selected pages at 375 pixels. Authenticated browser observations used seeded administrator storage; they were not full interactive login or CRUD journeys.

The API harness loads actual repository routes/controllers but disables `.env` loading and never establishes a database connection. It uses the project's fallback store. Selected tests capture model writes or substitute documented model/provider responses to isolate defects hidden by that store. Each result specifies its mode. Browser API calls were intercepted and redirected to this isolated server. No real payment, email, or database record was created.

**Usability and professional presentation**

Desktop strengths: consistent navigation, recognizable sections, clear primary actions, and visible status/balance groupings. Most inspected screens rendered with the fixture dataset, and neither browser showed document-wide horizontal overflow at the tested widths. This is a useful visual foundation.

Before a user pilot, prioritize trustworthy payment states, accurate totals, clear loading/error/empty distinctions, labeled forms, and mobile header layout. The dark sidebar's small secondary captions appear difficult to read; measure contrast before asserting accessibility compliance. Avoid overlong page titles and repeated “enterprise” wording where a shorter task label would be clearer. Include currency and billing period consistently, and distinguish pending verification from paid receipts.

Browser rendering did not exercise every modal, keyboard focus trap, destructive action, print layout or native accessibility feature. The generic JS-exception event array does not include React errors caught by ErrorBoundary; the corrupted-session screenshots are explicit evidence of a caught UI failure.

**Performance interpretation**

The 2.48/3.89 ms API timings measure only a local, small, in-memory fixture. They say nothing reliable about PostgreSQL joins, cloud latency, realistic tenant volumes, provider latency or concurrency capacity. Native export duration is build time, not mobile launch time. Initial browser timing is local/cached and was not used as a user-performance score.

The next meaningful performance test should use disposable PostgreSQL with representative tenant/payment history, concurrent administrators and tenants, controlled network latency, query plans, and p95/p99 timings. Include bill generation, full billing overview, reports, and reconnect after an outage. Validate transactions and isolation before increasing load.

**Limits and release follow-up**

Not executed: real PostgreSQL integration/migrations, real or provider-hosted sandbox payments, native app interaction on physical Android/iOS devices, Safari/Firefox, macOS/Linux clean installation, real network outages, load/concurrency tests, a current dependency-vulnerability audit, exhaustive CRUD/form validation, or a complete accessibility audit. Offline Expo dependency output is not a security audit. Browser tests did not validate real deployment CORS because traffic was intercepted.

Recommended repair order: QA-01 through QA-05 first; then persistent storage, authentication, approval transactions and payment integrity; then schema/deployment compatibility; then responsive/accessibility fixes and performance work. Require regression tests for every release-blocking finding and a complete disposable-database payment/application journey before approving production use.+
